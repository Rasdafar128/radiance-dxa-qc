## 1. Задача

На вход — денситометрическое исследование (DXA) в DICOM. Решение должно ответить:
пригодно ли исследование для клинической интерпретации, корректна ли укладка и область
измерения, а если нет — **какое именно нарушение**. Смысл сервиса не в распознавании
картинки, а в том, чтобы рентгенолаборант увидел ошибку до того, как пациент ушёл.

Обязательные области: **поясничный отдел позвоночника** и **проксимальный отдел бедра**.
Область определяется решением самостоятельно — в тестовых файлах подсказок не будет
(ответ на вопрос 15: суффиксов в именах файлов закрытого теста нет).

Обязательный функционал по условию: определение области и проекции → бинарная
классификация качества → оценка укладки → оценка области измерения → определение одного
или нескольких типов нарушения → структурированный отчёт.

Уточнение из ответов пп. 5–6:

- Отступы 3/2 см относятся только к бедру и отсчитываются от ROI по рис. 6.
  Эталонных координат в DICOM нет и в закрытом тесте не будет. Дополнительный ответ
  п. 4 уточняет смысл критерия: **полнота исследуемой зоны и выбор поля сканирования**,
  а не наличие сохранённого контура ROI. Алгоритм точного измерения отступов не задан.
- Для позвоночника полнота определяется верхними краями подвздошных костей снизу
  и половиной Th12 сверху, а не отступами бедра.
- Ось проходит по центрам тел позвонков, не по остистым отросткам, от верхнего
  визуализируемого позвонка к нижнему; вертикаль кадра совпадает с осью сканирования.
  Сколиоз при корректной оси сам по себе не делает снимок некачественным.
- Отдельной инструкции разметчика нет: ориентиры — ТЗ §2.3 с рисунками и нормальные
  примеры набора. Пограничные правила автоматического измерения остаются Q02.

Несколько нарушений перечисляются через `;`, при отсутствии — **пустое поле**.
Сторона (левое/правое бедро) в выходе не различается.

В пикселях этого сканера (см. §3): 3 см по вертикали ≈ **28,6 px**, 2 см по
горизонтали ≈ **33,3 px**. Размер поля зависит от кадра; ширина 300 px соответствует 18 см.

### 3.4 Визуальные особенности

Все изображения просмотрены на 16 листах; наблюдения — технические, без новых
клинических диагнозов и без изменения экспертных меток.

- Кадры содержат анатомическое изображение без нанесённых контуров ROI и ориентиров.
  Наблюдаются чёрный фон и ступенчатые границы поля; автоматически обрезать их нельзя:
  покрытие анатомии и отступы входят в задачу качества.
- Тонкие светлые дуги и другие структуры у границ видны на ряде кадров с меткой
  посторонних предметов. Центральный кроп может их удалить.
- S079 имеет светлые структуры в верхней части при нулевых флагах; это кандидат
  для проверки экспертом, а не установленная ошибка разметки (см. Q13).
- Встречается визуально искривлённая ось при нулевой метке наклона и комментарии
  «сколиоз». Изгиб позвоночника и угол выбранной общей оси нельзя автоматически отождествлять.
- Три изображения с протезами отличаются от размеченных бёдер; два из них — единственные
  кадры шириной 248. Нельзя оценить качество распознавания этой подгруппы без меток.
- Доля нулевых пикселей: медиана 38,1% для позвоночника и 53,2% для бёдер.
  Медиана доли `raw >= 250` у позвоночника без метки предметов — 0,482%, с меткой — 0,474%.
  Яркость сама по себе не подтверждает наличие металла.

Последний вариант пересчитан после ответа п. 8: 249 изображений из 100 исследований,

Исключены только три кадра с неизвестными критериями; в этих исследованиях есть другие
размеченные изображения. Прежнее исключение противоречащих итогам позвоночников отменено. Выбор из 10 000 назначений
с seed 42 сделан только по балансу меток, без оценки качества модели.
Это **кандидат протокола**, а не завершённая валидация и не окончательно очищенная разметка.
Исключения и решение о разбиении — в [PLAN §2](PLAN.md#2-данные-и-разбиение--до-обучения).

## 4. Формат выхода

Одна строка — одно изображение (одна анатомическая область) исследования.

| Колонка | Содержимое | Тип |
|---|---|---|
| `path_to_study` | путь к исследованию или файлу | String |
| `study_uid` | `StudyInstanceUID` из DICOM | String |
| `image_uid` | `SOPInstanceUID` из DICOM | String |
| `anatomical_region` | одна из двух строк §2 | String |
| `quality_class` | 0 — качественное, 1 — есть нарушение | Integer |
| `quality_prob` | вероятность нарушения, [0;1] — **разрешена ответом на вопрос 8** | Float |
| `violation_type` | строки §2 через `;`, пусто если нарушений нет | String |
| `processing_status` | `Success` / `Failure` | String |
| `time_of_processing` | время обработки, секунды | Float |

`quality_prob` добавляем для непрерывной оценки нарушения: бинарные решения теряют
информацию о ранжировании, нужную для ROC-AUC. При `Failure` неизвестные значения
оставляем пустыми; не подставляем 0 как признак качественного изображения.

Дополнительно (не обязательно, но оценивается): серия с визуализацией нарушения
(маска/контур/ключевые точки/тепловая карта), DICOM SR с текстовым описанием,
автокоррекция разметки, веб-интерфейс.

## 5. Технические требования

- **Контейнеризация обязательна** + скрипт сборки и запуска для Linux/UNIX.
- **API для пакетной обработки** тестового набора; на вход — архив, на выход —
  общая таблица и zip с дополнительными сериями (если функционал есть).
- По дополнительному ответу п. 3 сеть доступна при сборке: зависимости и точные веса
  можно скачивать по открытым ссылкам без учётных записей команды, с фиксацией версий
  и хешей. Отсутствие сети относится к инференсу готового образа.
- Финальный сервис работает локально, без обращения к внешним сервисам и передачи
  снимков наружу; среда обучения команды описывается отдельно и не входит в этот
  runtime-контракт.
- Все версии зафиксированы: библиотеки, рантайм, базовый образ.
- ≤ 3 минуты на исследование; **необработанных исключений нет** — любая ошибка
  становится строкой с `processing_status=Failure`, а не падением прогона.
- Воспроизводимость при повторном запуске на тех же данных.

## 6. Как оценивают

Общие критерии конкурсных баллов — в [CONTEST_RULES §2](CONTEST_RULES.md#2-сдача-отбор-и-финал).
Ниже — технические метрики задачи.

Ответ п. 9 и дополнительный ответ п. 2 определяют две группы метрик: корректность
изображения в целом, затем отдельные нарушения и macro-F1 по ним. Сравнение строки `violation_type`
целиком не заявлено. Переданную вероятность используют для ROC-AUC; скрипт оценки
не предоставляется. Формула объединения этапов/областей, условная фильтрация второго
этапа и учёт Failure не раскрыты — [Q03](QUESTIONS.md#q03--официальный-расчёт-метрик).

Метрики считаются **отдельно по каждой области и каждому типу нарушения** и в целом:
чувствительность, специфичность, balanced accuracy, F1, ROC-AUC / PR-AUC, macro-F1 по
типам, Dice/IoU при наличии локализации, время обработки и доля успешно обработанных
файлов. Приоритет — **F1 и ROC-AUC**. Метрики диагностической точности просят подавать
с **95% доверительными интервалами** (при 252 изображениях интервалы будут широкими —
это ограничение точности оценки; интервалы не компенсируют малое число позитивов).

## 7. Сдача

Процедура загрузки и подтверждения финала — в
[CONTEST_RULES §2](CONTEST_RULES.md#2-сдача-отбор-и-финал). По ответу п. 10 сдаётся
ссылка на публичный репозиторий со скриптом сборки/запуска; отдельной передачи образа
нет. Контейнер со всеми весами должен воспроизводиться из этой поставки.
Ниже — состав результата по ТЗ, а не два дополнительных срока сдачи.

**Промежуточная (MVP)**: обученная модель + скрипт инференса, чтение DICOM и пакетная
обработка, минимум бинарный класс, оценка разметки хотя бы для одной области, файл
результатов в согласованном формате, метрики на валидации, краткая инструкция,
описание ограничений и план доработки.

**Финальная**: контейнеризованный сервис со всеми весами, обе области и все классы
нарушений, скрипт сборки/запуска, устойчивая пакетная обработка закрытого набора,
структурированный файл результатов, полный комплект документации, презентация и
демо-сценарий, исходный код. Финальная проверка — экспертами на закрытых данных **без
участия команды**: всё, что не описано в документации, на проверке не существует.

инструкцией по сборке и запуску, описанием API, форматов входа/выхода, модели,
пред- и постобработки, известных ошибок; плюс руководство пользователя, руководство по
развёртыванию и описание процедуры обучения.
