# Рабочая документация

Здесь ведутся требования, исследования и решения команды. Корневой
[README](../README.md) — самостоятельное описание решения, его текущего состояния
и доступных способов запуска; ссылки на рабочую документацию в него не добавляем.

## Где хранить информацию

| Документ | Основное содержимое |
|---|---|
| [README проекта](../README.md) | назначение, обзор подхода, реализованные возможности, запуск и ограничения решения |
| [HACKATHON](HACKATHON.md) | требования задачи, таксономия и формат выхода; отдельно — измеренные факты о данных |
| [CONTEST_RULES](CONTEST_RULES.md) | общие правила конкурса, календарь, порядок участия и сдачи, ссылки на пункты источника |
| [PLAN](PLAN.md) | выбранный ML-план, предобработка, протокол валидации, порядок экспериментов и критерии принятия решений |
| [RESEARCH](RESEARCH.md) | внешние источники, кандидаты моделей и датасетов, версии, лицензии и результаты их проверки |
| [QUESTIONS](QUESTIONS.md) | вопросы, приоритеты, статусы, временные решения и подтверждения закрытия |
| [TEMPLATE](TEMPLATE.md) | правила реализации: границы компонентов, контракты, сохранение артефактов, проверки и упаковка |

## Как поддерживать порядок

1. Обновлять факт в профильном документе. Из других рабочих документов ссылаться
   на него; краткий обзор в корневом README не должен превращаться в копию протокола.
2. Различать требование организатора, измеренный факт, выбранный план и гипотезу.
   Для требований указывать источник, для измерений — набор и способ воспроизведения.
3. Ответы и статусы вопросов вести только в QUESTIONS. После ответа обновлять
   затронутые требования или план, сохраняя источник подтверждения.
4. При реализации обновлять состояние и команды в корневом README. Запланированное
   не описывать как работающее; результаты сопровождать версией данных и рецептом опыта.
5. Журналы опытов, прогнозы и метрики сохранять с артефактами по правилам TEMPLATE;
   принятое по результатам опыта изменение подхода фиксировать в PLAN.
6. Описывать общие области ответственности, а не полное дерево проекта. Конкретные
   пути нужны только для запуска, контракта или ссылки на реализацию. При переносе
   раздела обновлять входящие ссылки и якоря.
