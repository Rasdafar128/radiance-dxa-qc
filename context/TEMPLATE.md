# Правила репозитория

Где лежит код, как пишутся файлы, как решение превращается в контейнер и уезжает на
проверку. План разработки — в [PLAN.md](PLAN.md). Условие задачи и измерения
данных — [HACKATHON.md](HACKATHON.md). Реализованы `src/solution/`, итоговый E5 и API;
проверенное состояние и команды — в корневом README. Вопросы и временные решения — только в
[QUESTIONS](QUESTIONS.md); здесь хранятся правила реализации.

## 1. Главное деление

| Часть | Ответственность |
|---|---|
| Общая конфигурация | пути, контракт выхода и константы аппарата |
| Код инференса | чтение DICOM, модель, отчёт и API; входит в контейнер |
| Инструменты разработки | подготовка данных, разметка, обучение, валидация и сборка |

Правило одно и проверяемое: **нужно внутри контейнера на проверке — `src/solution/`,
иначе `src/utils/`.** Отсюда всё остальное:

| | `src/solution/` | `src/utils/` |
|---|---|---|
| зависимости | всё нужное для инференса и отчёта, с версиями в `docker/requirements.txt` | дополнительные инструменты анализа и обучения |
| импорты | относительные (`from .dicom import ...`); `src.utils` **запрещён** — в образе его нет, импорт упадёт | относительные внутри, `..config` и `..solution` наружу |

`src/utils` импортирует `src/solution` свободно (валидация зовёт модель, отчёт по
экспериментам зовёт инференс). Обратный импорт запрещён. Зависимости записи xlsx
относятся к сервису, если он выдаёт xlsx; назначение библиотеки определяет её место.

## 2. Контракт модели

```python
fit(df, verbose=True) -> self          # df — версия обучающего манифеста с принятыми исключениями
predict(images, verbose=True) -> pd.DataFrame   # quality_prob + violation_type на изображение
save(path) / Model.load(path)
```

Исходная `src.utils.data.table()` возвращает также строки с неизвестными целями;
она использует критерии C:I, не итоги J:L Excel. Это соответствует полученному
приоритету критериев. Перед `fit` фильтруем неизвестные цели по политике `criteria_v2` из
[PLAN §2](PLAN.md#2-данные-и-разбиение--до-обучения).

Начинаем с одного модуля подхода, сохраняющего этот интерфейс. `fit` вызывается только
при обучении; необязательные зависимости обучения не должны требоваться при импорте
инференса. `predict` не читает метки и не подстраивается под состав входного пакета.
Исследовательские веса пишутся в `artifacts/<подход>/`, в git не едут.
Итоговая поставка — `models/e5/`: JSON голов, конфигурации и хеши в git,
энкодеры вне git; подготовка через `src.utils.prepare_model`.

Нейросетевые веса — `state_dict` или ONNX; линейные головы и преобразования —
коэффициенты, смещения и параметры в массиве/JSON с проверкой совпадения предсказаний
после загрузки. Не сохраняем pickle целого пользовательского объекта. Вместе с весами
храним порядок классов, препроцессор, пороги, версии и идентификатор рецепта обучения.

## 3. Контракт выхода — одна функция, руками таблицу не собираем

Колонки, строки нарушений и разделитель — только из `src/config.py`
(`OUTPUT_COLUMNS`, `VIOLATIONS`, `VIOLATION_SEP`). Строки сохраняем дословно;
агрегация официальных метрик отслеживается в [Q03](QUESTIONS.md#q03--официальный-расчёт-метрик).

Два правила, которые нарушаются молча:

- **Каждому поданному изображению — строка.** Любой `continue` в цикле по файлам
  выкидывает строку из отчёта, и отчёт становится неполным, а не «почти полным».
- **Ошибка — это строка с `processing_status=Failure`**, а не исключение наружу.
  Условие требует отсутствия необработанных исключений: упавший файл заполняет что
  смог (`path_to_study`, uid'ы), остальное — пусто, причина — в лог.

`time_of_processing` меряется на изображение, полное время исследования проверяется
отдельно. При `Success` заполняем непрерывную `quality_prob` в [0;1]; при `Failure`
неизвестные значения остаются пустыми. Бинарный класс равен наличию хотя бы одного
выбранного типа нарушения. Общая вероятность и решения по типам могут расходиться;
эти случаи анализируем отдельно, не вводя несуществующих типов.

Эндопротез обрабатывается по общему пути бедра: сам по себе не задаёт Failure,
новый тип нарушения, положительную или отрицательную цель качества. Отсутствие
обучающих меток не является ошибкой обработки входного DICOM.

Ключ папки/Excel для обучения не подменяет StudyInstanceUID в ответе; исходные UID
сохраняются, даже если их синтаксис невалиден, но файл удалось обработать.
Дедупликация при обучении не должна удалять строки ответа при инференсе. Изображение
должно получать одинаковый результат отдельно, в другом порядке и в разных пакетах.

## 4. Артефакты валидации

Полный протокол разбиения, настройки, метрик и ДИ хранится в
[PLAN §7](PLAN.md#7-валидация-и-принятие-решений). Реализация обязана сохранять:

| Артефакт | Содержимое |
|---|---|
| Манифест | версия данных, изображения, группы, известные цели, исправления меток |
| Разбиения | внешние и внутренние фолды, числа позитивов; назначения фиксируются до обучения |
| Журнал опыта | гипотеза, версии весов, настройки, критерий принятия, время/VRAM и итоговое решение |
| Прогнозы | внешние OOF по изображениям, непрерывные оценки, выбранные классы, ошибки обработки |
| Метрики | значения, состав выборки, число пригодных ресэмплов, версия процедуры расчёта |

Замороженные независимые от набора эмбеддинги можно кэшировать заранее. Обучаемые
преобразования признаков сохраняются с моделью соответствующего фолда. Проверяем, что
загрузчик кэша не подменяет прогнозы на проверочных исследованиях обучающими.

Для непрерывного GPU-цикла нужен последовательный список конечных конфигураций,
отдельный каталог каждого запуска и статусы завершения фолдов. Checkpoint обучения
содержит веса, состояние оптимизатора, эпоху, seed/состояния генераторов и хеши
конфигурации/разбиения. После сбоя возобновляем незавершённую работу; завершённые
артефакты не перезаписываем другой конфигурацией. Несовпадение хешей останавливает
возобновление. При OOM один раз уменьшаем batch с сохранением эффективного размера;
повторный сбой завершает опыт с причиной, а не запускает бесконечные повторы.
Очередь не меняет метки, фолды или список гипотез по внешним метрикам.

## 5. Шапка файла

Первая строка модуля — `"""<Что это> — <зачем оно нужно>."""`. Дальше, через пустую
строку, — пример вызова и только то, чего не видно из кода: какая ловушка закрыта, что
и когда замерено, почему очевидный вариант плох. Ни истории, ни пересказа кода. Что
объясняет одну строку — живёт комментарием рядом с ней.

## 6. Нетривиальная логика оставляет после себя проверку

Один запускаемый `__main__` с `assert`, самый короткий, который падает, если логика
сломалась. Короткая проверка — `python -m src.utils.data`; полный технический аудит —
`python -m src.utils.audit`. Область проверки и измеренные факты — в
[HACKATHON.md §3.1](HACKATHON.md#31-что-видно-в-самих-файлах). Никаких
фреймворков и фикстур, пока не попросили.

Разошлось число — это либо сломанный код, либо новые данные; и то и другое надо
увидеть сразу, а не через неделю на графике метрики.

Для геометрии разделяем проверки: поворот/кроп проверяет согласованность преобразований,
независимая ручная разметка — абсолютную ошибку измерения. Для сервиса проверяем
сохранение всех строк, частичный сбой пакета, одинаковый ответ независимо от пакета
и совпадение предсказаний до/после сохранения весов.

## 7. Что внутри контейнера

Образ содержит код инференса, общую конфигурацию, веса и зависимости с
зафиксированными версиями. Сборка и запуск выполняются одним скриптом для Linux/UNIX.
Инструменты разработки остаются вне образа.

Сдаётся публичная ссылка на репозиторий со скриптом сборки/запуска, отдельный образ
не передаётся. **На этапе сборки сеть разрешена**: скрипт получает зависимости
и конкретные версии весов по открытым ссылкам без учётных записей команды, проверяет
хеши и включает веса в образ. Подтверждение — дополнительный ответ п. 3, см. Q10.
Способ распространения выбирается по лицензии конкретных весов; сборка проверяется
из чистого клона без локального кэша и личной авторизованной сессии разработчика.
Не считать приватный локальный `artifacts/` доступным проверяющим. На runtime скачиваний нет.

Пути импорта в контейнере и в репозитории совпадают (`src.solution.<модуль>`), чтобы
избежать расхождений загрузки модулей. На этапе инференса готового образа сети
нет: всё, что модель качает (веса претрейна, шрифты, кэш torch.hub), кладётся в образ
на этапе сборки. Обучающие данные в образ не включаем. Фиксируем версии зависимостей
инференса и обучения; текущий корневой `requirements.txt` пока не обеспечивает полной
фиксации версий. Для ML используются `requirements-train.txt` и закреплённые
runtime-зависимости `docker/requirements.txt`; CUDA-поставка дополнительно фиксирует
библиотеки в `docker/requirements-cuda.txt`. Исторический снимок среды E0
сохранён в `artifacts/e0/requirements.lock`.

Проверка перед сдачей: собрать образ, прогнать на `data/test` без подключения
репозитория и без сети, затем проверить валидный пакет с ошибочным файлом. Три отладочных
снимка проверяют интеграцию, но не качество классификации.

## 8. Данные и внешняя инфраструктура

Основания ограничений — в [CONTEST_RULES §4](CONTEST_RULES.md#4-конфиденциальность-и-инфраструктура).
Требования к публикации — в [Q08](QUESTIONS.md#q08--публичные-материалы); технический
выбор среды обучения здесь фиксируется как часть воспроизводимости.

18.09.2026 пользователь предоставил для разработки сервер **vast.ai**. Проверено SSH:
Ubuntu, Python 3.12.3, **RTX 3080 с 20 ГБ VRAM**, драйвер 580.126.09;
PyTorch 2.8.0+cu126 / Torchvision 0.23.0+cu126 проходят CUDA forward/backward.
Рабочая директория `/workspace/LCT26`, отдельная среда `.venv`. Это unprivileged
контейнер, Docker-in-Docker недоступен; драйвер принадлежит хосту и не меняется.
`/workspace` не является постоянным томом: результаты копируем обратно на Mac.
Личная RTX 3090, указанная в прежнем плане, пока не используется.
Аренда разрешена полученным ответом; исходные снимки не включаются в публичный git или образ.
Разрешённые примеры для конкурсной презентации готовятся отдельно по Q08.

Перед сменой GPU-среды: проверить драйвер/CUDA, выбрать совместимую среду
Python и пары PyTorch/Torchvision/Transformers по требованиям выбранных весов,
зафиксировать версии, проверить один forward/backward, VRAM и сохранение/возобновление.
Mac-среду не копируем как готовую CUDA-среду. На одной видеокарте тяжёлые опыты идут
последовательно; анализ сохранённых признаков и работа над API могут идти независимо.

Снимок текущей среды на 18.09.2026: Apple M4 Pro, 24 GiB памяти, macOS arm64;
проектная среда Python 3.14. PyTorch/Torchvision в ней не установлены. Docker Desktop
запущен в ходе реализации; Linux/amd64 CPU-образ E5 собран и проверен без сети.
Проверки итоговой поставки — в [DELIVERY](../docs/DELIVERY.md); исторические результаты
E0 сохранены в локальном `artifacts/e0/`.
На целевой конфигурации организаторов скорость ещё не измерена.
