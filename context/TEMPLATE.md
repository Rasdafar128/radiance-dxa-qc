# Правила репозитория

Где лежит код, как пишутся файлы, как решение превращается в контейнер и уезжает на
проверку. Про сам подход здесь ничего нет — он в [README.md](../README.md) и меняется;
правила — нет. Условие задачи и измерения данных — [HACKATHON.md](HACKATHON.md).

## 1. Главное деление

```
src/
  config.py          пути, контракт выхода, константы аппарата — знают обе половины
  solution/          ЕДЕТ В КОНТЕЙНЕР: чтение DICOM, модель, отчёт, API, точка входа
  utils/             ОСТАЁТСЯ ДОМА: разметка, фолды, метрики, валидация, картинки, сборка
```

Правило одно и проверяемое: **нужно внутри контейнера на проверке — `src/solution/`,
иначе `src/utils/`.** Отсюда всё остальное:

| | `src/solution/` | `src/utils/` |
|---|---|---|
| зависимости | только то, что стоит в образе: список фиксируется в `docker/requirements.txt` | любые: openpyxl, matplotlib, jupyter |
| импорты | относительные (`from .dicom import ...`); `src.utils` **запрещён** — в образе его нет, импорт упадёт | относительные внутри, `..config` и `..solution` наружу |

`src/utils` импортирует `src/solution` свободно (валидация зовёт модель, отчёт по
экспериментам зовёт инференс). Обратной стрелки нет — она единственный способ сломать
сдачу незаметно: дома всё работает, в контейнере `ModuleNotFoundError`.

## 2. Контракт модели

```python
fit(df, verbose=True) -> self          # df — таблица из src.utils.data.table()
predict(images, verbose=True) -> pd.DataFrame   # quality_prob + violation_type на изображение
save(path) / Model.load(path)
```

**Новый подход — один файл в `src/solution/` с этими четырьмя методами.** Валидация,
сборка образа и отчёты знают только эти имена, менять их под подход не придётся. Веса
пишутся в `artifacts/<подход>/`, в git не едут.

Формат весов — `state_dict` торча или onnx, не pickle целого объекта: класс модели
переименуется, и старые веса перестанут грузиться ровно в тот вечер, когда это дороже
всего.

## 3. Контракт выхода — одна функция, руками таблицу не собираем

Колонки, строки нарушений и разделитель — только из `src/config.py`
(`OUTPUT_COLUMNS`, `VIOLATIONS`, `VIOLATION_SEP`). Строки сравниваются дословно, и
опечатка в одной из них стоит целого класса в macro-F1.

Два правила, которые нарушаются молча:

- **Каждому поданному изображению — строка.** Любой `continue` в цикле по файлам
  выкидывает строку из отчёта, и отчёт становится неполным, а не «почти полным».
- **Ошибка — это строка с `processing_status=Failure`**, а не исключение наружу.
  Условие требует отсутствия необработанных исключений: упавший файл заполняет что
  смог (`path_to_study`, uid'ы), остальное — пусто, причина — в лог.

`time_of_processing` меряется на изображение, `quality_prob` заполняется всегда:
по колонке из 0/1 ROC-AUC вырождается, а это половина приоритетной метрики.

## 4. Валидация

- **Разбиение только по исследованию** — `GroupKFold(groups=study)`. В одном
  исследовании лежат два бедра одного пациента и побайтовые копии кадров; случайный
  сплит по изображениям даёт утечку (см. [HACKATHON.md §3.1](HACKATHON.md#31-что-видно-в-самих-файлах)).
- **Модель сравнивается по нескольким фолдам, а не по одному сплиту.** 252 изображения,
  у редкого класса 5–7 позитивов: разница двух конфигураций на одном фолде — это шум.
- **Метрики — по областям и по типам нарушений отдельно**, одно среднее число прячет
  ровно те классы, которые трудны. Формат таблицы метрик один и тот же на валидации,
  в логе прогона и в презентации.
- **Доверительные интервалы — бутстрапом по исследованиям**, а не по изображениям, и
  они будут широкими. Это аргумент в презентации (организаторы сами просят 95% ДИ), а
  не то, что надо прятать.
- Одно различие за сравнение. Разница двух прогонов, отличающихся пятью вещами, не
  говорит ничего.

## 5. Шапка файла

Первая строка модуля — `"""<Что это> — <зачем оно нужно>."""`. Дальше, через пустую
строку, — пример вызова и только то, чего не видно из кода: какая ловушка закрыта, что
и когда замерено, почему очевидный вариант плох. Ни истории, ни пересказа кода. Что
объясняет одну строку — живёт комментарием рядом с ней.

## 6. Нетривиальная логика оставляет после себя проверку

Один запускаемый `__main__` с `assert`, самый короткий, который падает, если логика
сломалась. Образец — `python -m src.utils.data`: печатает состав набора и проверяет
числа из [HACKATHON.md §3.1](HACKATHON.md#31-что-видно-в-самих-файлах). Никаких
фреймворков и фикстур, пока не попросили.

Разошлось число — это либо сломанный код, либо новые данные; и то и другое надо
увидеть сразу, а не через неделю на графике метрики.

## 7. Что внутри контейнера

```
docker/Dockerfile           базовый образ + requirements.txt, версии зафиксированы
docker/requirements.txt     зависимости solution-половины
run.sh                      сборка и запуск одной командой, Linux/UNIX
src/config.py
src/solution/               те же файлы, что и дома
artifacts/<подход>/         веса
```

Пути импорта в контейнере и в репозитории совпадают (`src.solution.<модуль>`) — код,
работающий локально, работает и на проверке, расходиться нечему. Интернета на проверке
нет: всё, что модель качает (веса претрейна, шрифты, кэш torch.hub), кладётся в образ
на этапе сборки.

Проверка перед сдачей: собрать образ, прогнать на `data/test` **на машине, где нет
репозитория** — это единственный способ поймать забытый файл и незаметный
`import src.utils`.

## 8. Удалённый сервер (vast.ai)

Данных 14 МБ в архивах — отдельного хранилища не нужно, но в git они не едут: это
медицинские снимки организатора.

```bash
git clone <repo> && cd LCT26
scp -P <port> data/raw/*.zip root@<host>:~/LCT26/data/raw/   # с локальной машины
python -m src.utils.data                                     # распакует и проверит
```

Обратно с сервера едут **только веса и журнал прогона** (`artifacts/`, `runs/`), тоже
`scp`. Код правится дома и приезжает через git — правки прямо на арендованной машине
теряются вместе с машиной.

## 9. Документация — часть сдачи, а не хвост

Финальную проверку эксперты проводят **без участия команды**: чего нет в документации,
того на проверке не существует. По условию (§5) README обязан содержать назначение и
ограничения, структуру проекта, системные требования и зависимости, инструкцию по
сборке и запуску контейнера, описание API, форматов входа/выхода, описание модели,
пред- и постобработки, перечень известных ошибок. Отдельно — руководство пользователя,
руководство по развёртыванию, описание процедуры обучения.

Пишется это по ходу, а не в последний вечер: раздел README про формат выхода — это
пересказ `config.OUTPUT_COLUMNS`, и если он расходится с кодом, расходится он молча.
