# Правила репозитория

Где лежит код, как пишутся файлы, как решение превращается в контейнер и уезжает на
проверку. Выбранный подход — в [README.md](../README.md). Условие задачи и измерения
данных — [HACKATHON.md](HACKATHON.md). Это целевые правила реализации: `src/solution/`,
контейнер и API ещё не созданы. Вопросы и временные решения — только в
[QUESTIONS](QUESTIONS.md); здесь хранятся правила реализации.

## 1. Главное деление

```
src/
  config.py          пути, контракт выхода, константы аппарата — знают обе половины
  solution/          ЕДЕТ В КОНТЕЙНЕР: чтение DICOM, модель, отчёт, API, точка входа
  utils/             ОСТАЁТСЯ ДОМА: разметка, фолды, метрики, валидация, картинки, сборка
```

Правило одно и проверяемое: **нужно внутри контейнера на проверке — `src/solution/`,
иначе `src/utils/`.** Отсюда всё остальное:

| | `src/solution/` | `src/utils/` |
|---|---|---|
| зависимости | всё нужное для инференса и отчёта, с версиями в `docker/requirements.txt` | дополнительные инструменты анализа и обучения |
| импорты | относительные (`from .dicom import ...`); `src.utils` **запрещён** — в образе его нет, импорт упадёт | относительные внутри, `..config` и `..solution` наружу |

`src/utils` импортирует `src/solution` свободно (валидация зовёт модель, отчёт по
экспериментам зовёт инференс). Обратный импорт запрещён. Зависимости записи xlsx
относятся к сервису, если он выдаёт xlsx; назначение библиотеки определяет её место.

## 2. Контракт модели

```python
fit(df, verbose=True) -> self          # df — таблица из src.utils.data.table()
predict(images, verbose=True) -> pd.DataFrame   # quality_prob + violation_type на изображение
save(path) / Model.load(path)
```

Начинаем с одного модуля подхода, сохраняющего этот интерфейс. `fit` вызывается только
при обучении; необязательные зависимости обучения не должны требоваться при импорте
инференса. `predict` не читает метки и не подстраивается под состав входного пакета.
Веса пишутся в `artifacts/<подход>/`, в git не едут.

Нейросетевые веса — `state_dict` или ONNX; линейные головы и преобразования —
коэффициенты, смещения и параметры в массиве/JSON с проверкой совпадения предсказаний
после загрузки. Не сохраняем pickle целого пользовательского объекта. Вместе с весами
храним порядок классов, препроцессор, пороги, версии и идентификатор рецепта обучения.

## 3. Контракт выхода — одна функция, руками таблицу не собираем

Колонки, строки нарушений и разделитель — только из `src/config.py`
(`OUTPUT_COLUMNS`, `VIOLATIONS`, `VIOLATION_SEP`). Строки сохраняем дословно;
агрегация официальных метрик отслеживается в [Q03](QUESTIONS.md#q03--официальный-расчёт-метрик).

Два правила, которые нарушаются молча:

- **Каждому поданному изображению — строка.** Любой `continue` в цикле по файлам
  выкидывает строку из отчёта, и отчёт становится неполным, а не «почти полным».
- **Ошибка — это строка с `processing_status=Failure`**, а не исключение наружу.
  Условие требует отсутствия необработанных исключений: упавший файл заполняет что
  смог (`path_to_study`, uid'ы), остальное — пусто, причина — в лог.

`time_of_processing` меряется на изображение, полное время исследования проверяется
отдельно. При `Success` заполняем непрерывную `quality_prob` в [0;1]; при `Failure`
неизвестные значения остаются пустыми. Бинарный класс равен наличию хотя бы одного
выбранного типа нарушения. Общая вероятность и решения по типам могут расходиться;
эти случаи анализируем отдельно, не вводя несуществующих типов.

Дедупликация при обучении не должна удалять строки ответа при инференсе. Изображение
должно получать одинаковый результат отдельно, в другом порядке и в разных пакетах.

## 4. Артефакты валидации

Полный протокол разбиения, настройки, метрик и ДИ хранится в
[README §7](../README.md#7-валидация-и-принятие-решений). Реализация обязана сохранять:

| Артефакт | Содержимое |
|---|---|
| Манифест | версия данных, изображения, группы, известные цели, исправления меток |
| Разбиения | внешние и внутренние фолды, числа позитивов; назначения фиксируются до обучения |
| Журнал опыта | гипотеза, версии весов, настройки, критерий принятия и итоговое решение |
| Прогнозы | внешние OOF по изображениям, непрерывные оценки, выбранные классы, ошибки обработки |
| Метрики | значения, состав выборки, число пригодных ресэмплов, версия процедуры расчёта |

Замороженные независимые от набора эмбеддинги можно кэшировать заранее. Обучаемые
преобразования признаков сохраняются с моделью соответствующего фолда. Проверяем, что
загрузчик кэша не подменяет прогнозы на проверочных исследованиях обучающими.

## 5. Шапка файла

Первая строка модуля — `"""<Что это> — <зачем оно нужно>."""`. Дальше, через пустую
строку, — пример вызова и только то, чего не видно из кода: какая ловушка закрыта, что
и когда замерено, почему очевидный вариант плох. Ни истории, ни пересказа кода. Что
объясняет одну строку — живёт комментарием рядом с ней.

## 6. Нетривиальная логика оставляет после себя проверку

Один запускаемый `__main__` с `assert`, самый короткий, который падает, если логика
сломалась. Образец — `python -m src.utils.data`: печатает состав набора и проверяет
числа из [HACKATHON.md §3.1](HACKATHON.md#31-что-видно-в-самих-файлах). Никаких
фреймворков и фикстур, пока не попросили.

Разошлось число — это либо сломанный код, либо новые данные; и то и другое надо
увидеть сразу, а не через неделю на графике метрики.

Для геометрии разделяем проверки: поворот/кроп проверяет согласованность преобразований,
независимая ручная разметка — абсолютную ошибку измерения. Для сервиса проверяем
сохранение всех строк, частичный сбой пакета, одинаковый ответ независимо от пакета
и совпадение предсказаний до/после сохранения весов.

## 7. Что внутри контейнера

```
docker/Dockerfile           базовый образ + requirements.txt, версии зафиксированы
docker/requirements.txt     зависимости solution-половины
run.sh                      сборка и запуск одной командой, Linux/UNIX
src/config.py
src/solution/               те же файлы, что и дома
artifacts/<подход>/         веса
```

Пути импорта в контейнере и в репозитории совпадают (`src.solution.<модуль>`), чтобы
избежать расхождений загрузки модулей. Интернета на проверке
нет: всё, что модель качает (веса претрейна, шрифты, кэш torch.hub), кладётся в образ
на этапе сборки. Обучающие данные в образ не включаем. Фиксируем версии зависимостей
инференса и обучения; текущий корневой `requirements.txt` пока не обеспечивает полной
фиксации версий.

Проверка перед сдачей: собрать образ, прогнать на `data/test` без подключения
репозитория и без сети, затем проверить валидный пакет с ошибочным файлом. Три отладочных
снимка проверяют интеграцию, но не качество классификации.

## 8. Данные и внешняя инфраструктура

Основания ограничений — в [CONTEST_RULES §4](CONTEST_RULES.md#4-конфиденциальность-и-инфраструктура).
Текущие решения для обработки и публикации — в [Q07](QUESTIONS.md#q07--внешняя-инфраструктура)
и [Q08](QUESTIONS.md#q08--публичные-материалы); здесь они не дублируются.

После выбора допустимой среды код переносится через git, артефакты — отдельно.
Снимки не включаются в репозиторий и образ инференса. Сценарий удалённого обучения
должен ссылаться на зафиксированное основание использования выбранной среды.
