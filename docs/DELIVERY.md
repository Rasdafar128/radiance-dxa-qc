# Поставка Radiance · проверка и демо

Состояние на 18.09.2026. ML-рецепт не менялся при упаковке: в `models/radiance/`
сохранены исходные веса, головы и пороги. Изменены имя, версия и размещение
происхождения модели; соответствие исходным параметрам проверено отдельно.
По умолчанию CLI и API загружают Radiance. Контейнер включает обе модели и лицензии.

Автономный CPU-check Radiance с загрузкой, двумя пакетами и HTTP-ошибками занял 118,96 с.
Наблюдаемая память одного контейнера во время инференса — около 4,27 GiB;
это замер в ходе проверки, не доказанный максимум для всех входных размеров.
Docker VM имела 7,75 GiB RAM. Скорость эмуляции не является оценкой CPU Linux-сервера.

Проверка CUDA-контейнера на реальной GPU ограничена инфраструктурой: предоставленная
vast.ai-среда сама является непривилегированным контейнером и не запускает Docker.
GPU-инференс проверяется там непосредственно в Python; Docker-сборка — отдельно.
Не выдаём Python CUDA-check за запуск GPU внутри сдаваемого образа.

Машинные результаты остаются локально в `artifacts/delivery-checks/`:
`container.json`, `checks_cuda.json`, `technical_predictions_cuda.csv`.
Повторные проверки версии 1.1 хранятся в `artifacts/radiance-checks/`.
Последний файл содержит идентификаторы входных исследований и не публикуется.

## Повторение проверки

```bash
python3 -m src.utils.prepare_model --verify-only
docker build --platform linux/amd64 -f docker/Dockerfile -t radiance:cpu .
python3 -m src.utils.check_delivery --image radiance:cpu --input data/test
# В тренировочной среде с полной выгрузкой:
HF_HUB_OFFLINE=1 python -m src.utils.check --device cuda
```

`check_delivery` запускает и удаляет только собственный временный контейнер.
Подключает входные данные read-only; веса и код берёт из образа. Без `--image`
проверяет подготовку комплекта на небольших синтетических файлах.

## Демо за несколько минут

1. Подготовить ZIP из трёх отладочных DICOM организаторов.
2. Запустить `./docker/run.sh cpu` или CUDA-вариант на подходящем Linux-хосте.
3. Показать `/health`: обе итоговые модели, устройство, состояние `ok`.
4. Отправить ZIP в `/batch`, открыть CSV: три строки, UID, область, качество,
   типы нарушений, `Success`, время.
5. Повторить с одним повреждённым файлом: для него отдельная строка `Failure`,
   исходные предсказания сохраняются. Не представлять отладочные файлы как тест качества.
6. Показать [карточку Radiance](../models/radiance/README.md): метрики, интервалы, независимый тест
   отсутствует, редкие классы и перенос на другие аппараты требуют проверки.
