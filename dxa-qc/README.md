# DXA QC — исследовательский исходник объединённой версии 1.0

> **Рабочая поставка — [Radiance 1.0 в корне репозитория](../README.md).**
> Эта папка сохраняет происхождение решений ветки `dxa-qc` и её эксперименты.
> В основной сервис перенесены признаки оси и поля бедра; второй API, ещё два
> энкодера, DICOM SR и экспериментальные наложения в поставку не входят.
> Метрики ниже исторические: их пороги и правила подбирались на оценочных OOF.
> Актуальное сравнение на одинаковых фолдах — [UNIFICATION](../research/UNIFICATION.md).

ЛЦТ 2026, кейс 04 (ДЗМ / Центр диагностики и телемедицины).

Сервис получает DICOM-исследования денситометрии (DXA) поясничного отдела позвоночника и проксимального отдела бедра. По каждому изображению он:

- определяет анатомическую область (и сторону бедра);
- оценивает качество укладки и области сканирования по критериям ТЗ;
- выдаёт `quality_class`, вероятность `quality_prob` и перечень нарушений из официального словаря;
- объясняет решение: измеренные величины, визуализация на снимке, DICOM SR.

Работает полностью локально, без обращения к внешним сервисам.

**Качество** (10× повторённая 5-fold кросс-валидация, разбиение по исследованиям):
ROC-AUC **0.842** [0.783–0.894], F1 класса «есть нарушение» **0.663** [0.568–0.745],
macro-F1 по четырём официальным названиям нарушений **0.606**, классификатор области — accuracy 1.000.
Полный отчёт: `reports/metrics.md`.

## 1. Возможности и ограничения

**Что умеет**

| Функция ТЗ | Реализация |
|---|---|
| Определение области | Классификатор на эмбеддингах DINOv2, не зависит от тегов и имён файлов. Сторона бедра определяется по анатомии |
| Качественное / нарушение | `quality_class` (0/1) + калиброванная `quality_prob` ∈ [0;1] |
| Типы нарушений | Позвоночник: «Некорректная укладка», «Не выравнена ось позвоночника», «Присутствуют посторонние предметы». Бедро: «Некорректная укладка», «Некорректная область интереса». Несколько нарушений через `;` |
| Объяснение | Колонка `details` (угол оси, отступы в мм, вероятности по критериям). Для каждого снимка PNG и DICOM Secondary Capture с разметкой: ось, отступы, малый вертел. Для каждого исследования DICOM SR (Basic Text SR) |
| Пакетная обработка | CLI и REST API: папка / zip → `results.csv`, `results.xlsx`, `overlays.zip`, `sr.zip` |
| Веб-интерфейс | Загрузка, прогресс, таблица с фильтрами, просмотр визуализации, отметка «согласен / не согласен» специалиста |
| Устойчивость | Битый файл или исследование дают строку `processing_status=Failure` с текстом ошибки, пакет не прерывается |

**Ограничения**

- Модели обучены на 100 исследованиях одного аппарата (GE Lunar Prodigy Advance, экспорт CR 8 бит). Позитивных примеров по отдельным критериям мало (6–36), поэтому доверительные интервалы метрик широкие.
- Изображения без экспертной разметки (эндопротезы) в обучении не участвуют. Сервис помечает подозрение на металлоконструкцию в `details`.
- Масштаб: принят изотропный пиксель 0,6 мм (см. раздел 6.3). Геометрические признаки масштабо-инвариантны для модели, но значения в мм в пояснениях зависят от этого допущения.
- Разметка ROI программы денситометра (L1–L4, шейка) в выгрузке отсутствует, поэтому оценивается область сканирования, а не ROI-боксы.

## 6. Данные

### 6.1 Вход
Папка любой вложенности, zip-архив или отдельный файл. Файлы распознаются по расширению `.dcm` или по
преамбуле `DICM`. Файлы группируются в исследования по `StudyInstanceUID` (при отсутствии — по папке).
Побайтно одинаковые изображения внутри исследования анализируются один раз.

### 6.2 Выход
Основной файл для проверки — **`results.xlsx`** (лист `results`, плюс лист `summary` со сводкой); так рекомендовали организаторы.
Дублирующий **`results.csv`**: разделитель полей — запятая `,`, кодировка UTF-8 без BOM, десятичный разделитель — точка,
строки с запятыми/переносами заключаются в двойные кавычки (RFC 4180), пустое значение — пустая ячейка.

Одна строка — один DICOM-файл.

| Колонка | Тип | Описание |
|---|---|---|
| path_to_study | str | путь к файлу относительно входной папки |
| study_uid | str | StudyInstanceUID |
| image_uid | str | SOPInstanceUID |
| anatomical_region | str | «Поясничный отдел позвоночника» / «Проксимальный отдел бедра» |
| quality_class | int | 0 — качественное, 1 — есть нарушение (пусто при Failure) |
| violation_type | str | нарушения через `;`, пусто если нет |
| processing_status | str | Success / Failure |
| time_of_processing | float | секунды (время исследования, делённое на число его файлов) |
| quality_prob | float | калиброванная вероятность нарушения, [0;1] |
| side | str | R / L для бедра (информативно) |
| details | str | измерения и вероятности по критериям |
| error | str | текст ошибки при Failure |

### 6.3 Обучающие данные и решения по ним
- **Структура.** 100 исследований, 499 файлов, но только **252 уникальных изображения** (остальное — побайтные дубли). 99 снимков позвоночника и 153 бедра, из них размечено 249.
- **Сторона бедра** определяется по анатомии: в радиологической конвенции таз находится медиальнее диафиза. Метки правого и левого бедра из разметки легли на снимки **без единого конфликта** (72 правых, 78 левых). Три неразмеченных снимка — ровно эндопротезы (#66 правое, #70 оба).
- **Шум разметки.**
  - «Итог» противоречит критериям в #6, #11 (итог 1, критерии 0) и #35 (ось 1, итог 0). Модели критериев учатся на колонках критериев, калибровка — на «Итоге». Список формируется в `reports/label_noise.csv`.
  - Сколиоз размечен непоследовательно.
- **Масштаб.** Организаторы указали 0,6 × 1,05 мм. На выгрузке измерено:
  - медианный шаг позвонков 53 px;
  - высота поля позвоночника 315 px;
  - ExposedArea в согласованных записях даёт 0,60–0,61 мм по обеим осям;
  - анатомия не сплющена.

  Всё это указывает на изотропный пиксель ~0,6 мм после экспорта. Используется 0,6 мм (`config.PIXEL_MM`), вопрос направлен экспертам.
- **Закрытый тест** по разъяснению организаторов снят на аппаратах той же модели, с теми же типами исследований и стандартными размерами изображений; дополнительных тегов и меток зоны не будет. Область определяется классификатором по пикселям (CV-accuracy 1.000), размер изображения согласуется с ним.
- **Разбиение.** Повторная 5-fold кросс-валидация, группировка по исследованию, стратификация по «Итогу». Два бедра одного пациента никогда не попадают в разные фолды.

## 7. Модель

**Предобработка.** Любой DICOM приводится к 8-битному полутоновому изображению: modality LUT, инверсия MONOCHROME1, перцентильная нормировка для >8 бит. Левое бедро отражается в каноническую ориентацию.

**Признаки.**
1. *Геометрия* (интерпретируемые измерения, `geometry.py`):
   - позвоночник: робастная осевая линия и её угол к вертикали, кривизна, уровень гребней подвздошных костей, число позвонков над гребнями, яркие тонкие структуры (косточки белья, металл) через top-hat;
   - бедро: контур бедренной кости, ширина диафиза (анатомический масштаб), отступы от большого вертела до верхнего и латерального краёв, выступ малого вертела на медиальном контуре, длина скана ниже малого вертела.
2. *Эмбеддинги* четырёх замороженных foundation-моделей, CLS + средний патч-токен:
   - **DINOv3-L/16** (Meta, 448 px) — основной энкодер для укладки позвоночника, посторонних предметов и ротации бедра;
   - **MedImageInsight** (Microsoft, DaViT, 512 px, L2-нормированные признаки) — медицинский энкодер, дополняет DINOv3 на позвоночнике;
   - **DINOv2 ViT-B/14** (518 px) — классификатор области и критерий оси;
   - **RAD-DINO** (ViT-B/14, предобучен на рентгенограммах, 518 px) — область интереса бедра.

   Ни один энкодер не дообучается. Для позвоночника эмбеддинги усредняются с отражённым снимком, левое бедро приводится к канонической ориентации отражением.

**Модели** (`config.SPEC`). Для каждого критерия — 1–3 маленькие L2-логистические регрессии на отдельных блоках признаков, их логиты усредняются. При 100 исследованиях малое число параметров надёжнее стекинга (проверено вложенной кросс-валидацией, см. 7.1). Дообучение CNN (`experiments/finetune_cv.py`) проверено и уступает (см. 7.2).

| Критерий | Блоки | ROC-AUC |
|---|---|---|
| Позвоночник: укладка | гребни и уровни + DINOv3-L + MedImageInsight | 0.855 |
| Позвоночник: ось | угол осевой линии + DINOv2 | 0.828 |
| Позвоночник: посторонние предметы | top-hat / насыщенные объекты + DINOv3-L + MedImageInsight | 0.909 |
| Бедро: укладка / ротация | DINOv3-L; **контекст второго бедра** (ошибки ротации обычно двусторонние: отношение шансов ≈ 20) | 0.833 |
| Бедро: область интереса | высота скана, отступы в мм + RAD-DINO | 0.900 |

Состав блоков подобран перебором на повторной групповой кросс-валидации (`experiments/spec_search.py`,
полный лог — `reports/spec_search.csv`). Измерения геометрии считаются и показываются врачу независимо
от того, входят ли они в спецификацию модели: у ротации бедра они не улучшали ROC-AUC, но остаются
в `details` и на визуализации.

**Постобработка.**
- P(нарушение) = noisy-OR вероятностей критериев с Platt-калибровкой.
- `quality_class` — по порогу, максимизирующему F1 на OOF.
- `violation_type` — критерии выше своих порогов; если общий класс 1, а ни один критерий не прошёл порог, указывается наиболее вероятный.

Полный отчёт: `reports/metrics.md`, предсказания по каждому снимку: `reports/oof_predictions.csv`.

|---|---|---|---|---|---|---|---|
| Позвоночник | укладка | 99 | 6 | 0.500 | 1.000 | 0.667 [0.000–1.000] | 0.855 [0.565–1.000] |
| Позвоночник | ось | 99 | 10 | 0.900 | 0.663 | 0.367 [0.182–0.531] | 0.828 [0.721–0.921] |
| Позвоночник | посторонние предметы | 99 | 17 | 0.706 | 0.951 | 0.727 [0.529–0.882] | 0.909 [0.815–0.984] |
| Позвоночник | любое нарушение | 99 | 32 | 0.625 | 0.896 | 0.678 [0.522–0.800] | 0.816 [0.720–0.902] |
| Бедро | укладка / ротация | 150 | 36 | 0.722 | 0.816 | 0.627 [0.462–0.758] | 0.833 [0.743–0.910] |
| Бедро | область интереса | 150 | 7 | 0.714 | 0.986 | 0.714 [0.250–0.957] | 0.900 [0.667–1.000] |

F1 по официальным типам нарушений: «Некорректная укладка» 0.626, «Не выравнена ось позвоночника» 0.500,
«Присутствуют посторонние предметы» 0.727, «Некорректная область интереса» 0.571; **macro-F1 0.606**.

### 7.2 Как выбирался состав признаков

**Перебор по каждому критерию** (`experiments/spec_search.py`, 5 повторов групповой CV, ROC-AUC):

Все столбцы, кроме последнего, — геометрия плюс указанный энкодер; «—» в шапке значит «только геометрия».

| Критерий | — | DINOv2 | RAD-DINO | DINOv3-L | MII | DINOv3-L + MII | без геометрии, DINOv3-L | выбрано |
|---|---|---|---|---|---|---|---|---|
| Позвоночник: укладка | 0.580 | 0.776 | 0.685 | 0.819 | 0.823 | **0.844** | 0.831 | геом + DINOv3-L + MII |
| Позвоночник: ось | 0.769 | **0.801** | 0.522 | 0.769 | 0.558 | 0.646 | 0.688 | геом + DINOv2 |
| Позвоночник: предметы | 0.806 | 0.767 | 0.810 | 0.874 | 0.885 | **0.902** | 0.844 | геом + DINOv3-L + MII |
| Бедро: ротация | 0.585 | 0.672 | 0.692 | 0.785 | 0.649 | 0.760 | **0.799** | DINOv3-L |
| Бедро: область интереса | **0.901** | 0.882 | 0.900 | 0.864 | 0.887 | 0.861 | 0.777 | геом + RAD-DINO |

Читается так: геометрия незаменима там, где критерий ТЗ сам сформулирован как измерение
(ось, область интереса), а сильные энкодеры выигрывают там, где критерий описывает вид укладки
целиком. Медицинский MedImageInsight дополняет DINOv3-L на позвоночнике, но не на бедре.
У области интереса ROC-AUC геометрии и «геометрия + RAD-DINO» совпадают (0.901 против 0.900),
но PR-AUC выше с энкодером (0.755 против 0.683), а F1 считается именно в области редкого класса —
поэтому оставлен RAD-DINO.

**Прямая голова «есть нарушение»** (`experiments/any_blend.py`). Со старым составом признаков
подмешивание отдельной головы, обученной на итоговом вердикте, давало +0.04 ROC-AUC; после перехода
на DINOv3-L и MedImageInsight noisy-OR по критериям догнал её, и смесь перестала окупаться
(`ANY_BLEND = 0`). Механизм оставлен параметром — он снова понадобится, если разметка станет полнее.

**До и после — на строгом протоколе** (`experiments/protocol_compare.py`: 3 внешних групповых фолда,
пороги и калибровка только внутри train — заметно жёстче, чем 5-fold):

| Состав признаков | seed 42: F1 / ROC-AUC / macro-F1 | seed 137: F1 / ROC-AUC / macro-F1 |
|---|---|---|
| прежний (DINOv2 + RAD-DINO) | 0.422 / 0.647 / 0.350 | 0.535 / 0.753 / 0.384 |
| **текущий (DINOv3-L + MII + DINOv2 + RAD-DINO)** | **0.518 / 0.756 / 0.428** | **0.601 / 0.825 / 0.474** |

Прирост воспроизводится на обоих разбиениях и на протоколе, который не использовался при подборе —
значит, дело не только в подгонке состава признаков под кросс-валидацию.

**Что проверялось и не пошло в решение:** стекинг на эмбеддингах (переобучается на 100 исследованиях),
end-to-end дообучение ConvNeXt-Nano (ROC-AUC ротации 0.61 против 0.83 у замороженного DINOv3-L),
контекст второго бедра для области интереса (не даёт прироста, `CONTEXT_BETA["roi"] = 0`).

### 7.3 Объяснение решения

- **Колонка `details`** — по каждому критерию: вердикт («норма» или «НАРУШЕНИЕ»), измерение с допуском из ТЗ и вероятность модели. Пример: `ось: норма — наклон 1.6° при допуске 5°, риск 0.32 ≤ 0.41 | посторонние предметы: НАРУШЕНИЕ — есть яркие тонкие включения, риск 1.00 > 0.41`. «Риск» — вероятность нарушения по этому критерию, знак показывает, с какой стороны от порога она легла.
- **Правило для оси.** При измеренном наклоне менее `AXIS_MIN_ANGLE_DEG` = 3° нарушение «Не выравнена ось позвоночника» не выставляется, каким бы ни был выход модели: допуск ТЗ — 5°, и 2° остаётся на погрешность измерения. Порог подобран перебором на OOF (`experiments/axis_gate.py`): F1 по оси 0.417 → 0.500, macro-F1 0.591 → 0.606. На `quality_class` и его ROC-AUC правило не влияет вовсе — оно фильтрует только `violation_type`.
- **Визуализация** (PNG и DICOM SC): ось позвоночника и вертикаль с углом, уровень гребней подвздошных костей (рисуется только при уверенном обнаружении), отступы бедра в мм, метка малого вертела. Внизу кадра — вердикты по критериям и легенда обозначений.
- **Подсветка посторонних предметов** строится гистерезисом по white top-hat: яркие тонкие «ядра» (top-hat > 40 и яркость > 150) наращиваются до целого объекта по мягкому порогу (top-hat > 12 и яркость > 90). Ложные срабатывания на краях костей отсекаются по размеру объемлющей костной области: у косточек белья она 350–500 px, у краёв подвздошных костей 1000–1500 px, у позвоночника около 19 000 px, порог `MAX_ENCLOSING_BONE_PX` = 700.

## 8. Обучение и дообучение

`python scripts/train.py --data <папка с «Исследования» и «разметка.xlsx»> --reps 10`:
1. Собирает уникальные изображения и метки, определяет стороны, пишет отчёт о шуме разметки.
2. Считает признаки (кэш `artifacts/features.pkl`).
3. Обучает классификатор области и оценивает его на CV.
4. Проводит повторную кросс-валидацию, подбирает пороги и калибровку, считает метрики с кластерным bootstrap 95% ДИ.
5. Обучает финальные модели на всех данных и сохраняет их в `weights/`.

Для дообучения на новых данных достаточно добавить исследования и строки разметки в том же формате
и перезапустить скрипт. Отметки специалистов из веб-интерфейса (`feedback.jsonl`) можно использовать как
дополнительную разметку.

## 9. Известные ошибки и их обработка

| Ситуация | Поведение |
|---|---|
| Не-DICOM / повреждённый файл | строка `Failure`, `error=invalid DICOM…` |
| DICOM без изображения (SR, PR) | `Failure`, `error=no PixelData` |
| Исключение при анализе исследования | все файлы исследования `Failure` с текстом ошибки, пакет продолжается |
| Нетипичное изображение (другая область, скриншот) | обрабатывается, в `details` предупреждение |
| Эндопротез / металлоконструкция на бедре | обрабатывается, в `details` предупреждение |
| Контур бедра не выделен | признаки геометрии импутируются, в `details` пометка |
| Исследование дольше 180 с | предупреждение в логе |
| Визуализация не построилась | таблица результатов формируется, ошибка в логе |

## 10. Руководство пользователя (веб-интерфейс)
1. Откройте `http://<сервер>:8000`.
2. Перетащите zip с исследованиями или DICOM-файлы.
3. После обработки появятся сводка и таблица. Фильтры: «С нарушениями», «Качественные», «Ошибки».
4. Нажмите на строку, чтобы открыть визуализацию и пояснение. Кнопками «Согласен / Не согласен» специалист фиксирует оценку.
5. Скачайте XLSX/CSV, архив визуализаций (DICOM SC) и DICOM SR для загрузки в PACS.

## 11. Данные, лицензии, конфиденциальность

- Обезличенные данные организаторов **не входят в репозиторий** (конфиденциальная информация по правилам конкурса); код ожидает их по пути `--data`.
- Сторонние компоненты: DINOv2 (Meta, Apache-2.0), DINOv3-L (Meta, отдельная лицензия — `licenses/DINOv3.md`), MedImageInsight (Microsoft, MIT — `licenses/MedImageInsight.txt`), RAD-DINO (Microsoft; авторы указывают, что чекпоинт предназначен для исследований и не для клинической практики), PyTorch, timm, transformers, pydicom, scikit-learn, FastAPI. Сводка — `licenses/README.md`.
- Веса энкодеров в репозиторий не кладутся: публичные скачивает `scripts/download_weights.py`, DINOv3-L и MedImageInsight берутся из релиза команды и раскладываются `scripts/adapt_release_weights.py`.
- Сервис работает полностью локально: веса вшиты в контейнер, пакетный режим запускается с `--network none`, обращений к внешним ресурсам нет.

**Что проверено на целевом Linux x86_64 (без Docker, эквивалент шагов Dockerfile):**
1. `torch==2.14.0+cpu` и `torchvision==0.29.0+cpu` устанавливаются с индекса PyTorch CPU, остальные версии из `requirements.txt` ставятся без конфликтов;
2. чистая копия только тех файлов, которые копирует Dockerfile (`dxaqc`, `scripts`, `weights`), запускается в свежем окружении и обрабатывает исследования при отключённой сети (`HF_HUB_OFFLINE=1`, весь трафик в тупиковый прокси) и без GPU — 0 ошибок, формируются `results.csv/xlsx`, `overlays.zip`, `sr.zip`;
3. размер: зависимости 1,4 ГБ + веса 3,4 ГБ (четыре энкодера), итоговый образ ожидается около 5,5–6 ГБ.

Сама команда `docker build` выполняется на машине с Docker: GPU-инстанс, на котором велась разработка, — непривилегированный контейнер (user namespaces запрещены seccomp), поэтому ни Docker, ни rootless buildah/podman в нём не работают.
