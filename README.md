# ЛЦТ 2026 — контроль качества денситометрии (ДЗМ)

Сервис по DXA-исследованию в DICOM определяет анатомическую область, наличие и типы
нарушений качества. Результат — таблица по изображениям; сдача — контейнер с пакетным
API. Приоритетные метрики: **F1 и ROC-AUC**.

## 1. Решение: простой бейзлайн и проверяемая геометрия

**Начинаем с одного замороженного бэкбона и регуляризованных линейных голов.**
Геометрия — основная гипотеза улучшения и объяснения, но сначала проверяем её на ручных
измерениях. Массовую разметку и обучение сегментации начинаем после этой проверки.

```text
DICOM → чтение и предобработка → определение области
                                  │
                                  ├─ признаки полного изображения → головы нарушений
                                  │
                                  └─ проверенные анатомические измерения (после пилота)
                                               │
                             выбранное правило / простое слияние
                                               │
                           оценки нарушений → пороги → таблица
                                               └─ оверлей, если измерение надёжно
```

| Компонент | Решение сейчас | Условие расширения |
|---|---|---|
| Признаки изображения | один бэкбон, полный кадр | второй бэкбон только после сравнения на одинаковых фолдах |
| Геометрия | ручной пилот, первой проверяем ось позвоночника | измерение воспроизводимо и связано с экспертной меткой |
| Сегментация / точки | выбор после пилота | обучаем только ориентиры, необходимые для полезных измерений |
| Слияние | сначала отдельные ветки | объединение улучшает внешнюю проверку относительно обеих веток |
| Синтетика | отдельный эксперимент | выигрыш на реальных проверочных снимках |
| DICOM SR | после рабочего обязательного выхода | остаётся время на проверку совместимости |

## 3. Предобработка

| Этап | Решение |
|---|---|
| Чтение | проверить декодирование, форму, битность и фотометрическую интерпретацию; ошибка одного файла не обрывает пакет |
| Физическая сетка | использовать валидный `PixelSpacing`, при отсутствии — подтверждённые для данного сканера 1,05 мм по Y и 0,60 мм по X; источник масштаба записывать |
| Измерения | координаты переводить в мм: `x_mm = x_px × sx`, `y_mm = y_px × sy`; изотропный ресемплинг допустим, но не обязателен для корректной геометрии |
| Яркость | сохранять исходный массив; учитывать MONOCHROME1 до интерпретации яркости; нормализация не должна делить на ноль на постоянном кадре |
| Вход бэкбона | сохранять пропорции; использовать размер и нормализацию выбранных весов, а не общий размер 448 для всех моделей |
| Геометрические преобразования | хранить преобразование координат, чтобы измерения и оверлей вернулись в исходную сетку |

Для угла **к вертикали** при заданном размере пикселя:

```text
tan θ_физ = (0,60 / 1,05) × tan θ_пикс
5° в физической сетке ≈ 8,7° в исходных пикселях
```

Для изотропной сетки 0,60 мм растягиваем Y в 1,75 раза. Бинарные маски преобразуем
методом ближайшего соседа. Признаки исходного насыщения извлекаем **до интерполяции и
обрезки яркости**. Для другого аппарата без достоверного масштаба миллиметры не выдаём
как измеренный факт.

`raw >= 250` — кандидат признака для текущих 8-битных MONOCHROME2, **не детектор металла**.
Измерения — в [аудите набора](context/HACKATHON.md#31-что-видно-в-самих-файлах).
Форму и положение компонент проверяем отдельным опытом.

## 4. Бейзлайн внешнего вида

- Область: голова «позвоночник / бедро» на замороженных признаках. Правило ширины
  300 px — контроль расхождений для текущего аппарата, не универсальное определение.
- Нарушения: пять бинарных целей, применимых к своей области; L2-регуляризованная
  логистическая регрессия. Линейная голова тоже может переобучаться.
- Первым контрольным кандидатом берём один доступный ImageNet-бэкбон. Медицинский
  бэкбон из [RESEARCH](context/RESEARCH.md) сравниваем следующим отдельным опытом,
  с учётом [Q06](context/QUESTIONS.md#q06--сторонние-библиотеки-веса-и-датасеты).
- Масштабирование признаков и подбор силы регуляризации выполняются внутри train.
  Вариант с `class_weight=balanced` сравнивается с обычным; калибровка вероятностей
  не предполагается автоматически.
- Для `quality_prob` в бейзлайне — отдельная бинарная голова на цель «есть хотя бы одно
  нарушение» для каждой области. Она не требует второго уровня стекинга.
- Кропы по анатомии и TTA добавляются отдельно. Применимость отражения проверяется
  для всех используемых признаков; знак геометрической оси требует преобразования.

Оценка области должна входить в сквозную валидацию: основная метрика включает ошибки
маршрутизации. Результат с заранее известной областью — только диагностический срез.

## 5. Геометрия: сначала проверить смысл измерений

### 5.1 Пилот ручной разметки

На обучающей части первого заранее зафиксированного внешнего разбиения выбрать
20–30 снимков: обе области, доступные редкие нарушения, нормальные и пограничные случаи.
Внешнюю проверочную часть для разработки определений не использовать.

| Что сделать | Что получить |
|---|---|
| Зафиксировать инструкцию | какие точки/контуры отмечать, как считать ось, что считать ROI и обрезанной структурой |
| Разметить ориентиры и измерить вручную | таблица измерений рядом с исходными экспертными целями |
| Повторить часть разметки независимо | оценка расхождений измерителей; без второго эксперта — повторная разметка с указанным ограничением |
| Сравнить ручное правило с метками | ошибки по случаям и причины: определение, разметка, патология, неполная наблюдаемость |
| Проверить помощь SAM на части снимков | фактическое время правки и качество нужных контуров |

Этот пилот служит для выбора метода, **не для заявления финальной точности**. Инструкцию
после пилота фиксируем; последующее изменение по ошибкам внешней проверки считается
новым циклом разработки, а прежняя проверка перестаёт быть независимой.

### 5.2 Измерения и ограничения

| Цель | Кандидат измерения | Зависимость определения |
|---|---|---|
| Ось позвоночника | угол линии по позвонкам к вертикали | [Q02](context/QUESTIONS.md#q02--анатомические-ориентиры-и-правила-измерения) |
| Укладка позвоночника | видимость Th12 и гребней относительно кадра | [Q02](context/QUESTIONS.md#q02--анатомические-ориентиры-и-правила-измерения) |
| Укладка бедра | выраженность малого вертела и видимость структур | [Q02](context/QUESTIONS.md#q02--анатомические-ориентиры-и-правила-измерения) |
| ROI бедра | отступы от области измерения до границ кадра | [Q01](context/QUESTIONS.md#q01--определение-roi) |

Для каждого ориентира различаем «найден», «обрезан кадром», «не удалось определить».
Отсутствие маски не равно нарушению укладки. При недостоверной геометрии используем
заранее проверенную ветку внешнего вида и не рисуем уверенное объяснение в миллиметрах.

### 5.3 Автоматизация и проверка

- Выбираем точки или маски по результатам пилота. nnU-Net 2D — кандидат, а не
  обязательная стадия; полная сегментация всех костей не нужна для одного угла.
- Анатомическую разметку можно подготовить для всего набора по фиксированной инструкции.
  Обучать локализатор для внешнего фолда можно только на его train-исследованиях.
- Для обучения головы на автоматической геометрии получаем предсказания локализатора
  вне его обучающих исследований, чтобы не подменять ошибочные маски идеальными.
- Точность угла и расстояний оцениваем по независимым ручным измерениям: абсолютная
  ошибка, систематическое смещение, доля случаев без надёжного измерения.
- Повороты и кропы проверяют **согласованность преобразований**, а не абсолютную точность.
  Сохранение ошибки после поворота не означает правильного исходного измерения.

Критерии из [таксономии](context/HACKATHON.md#2-таксономия-нарушений) сохраняем как нормативные. Порог обученного решения
может отличаться, но показываем его отдельно: нельзя называть оптимизированный по F1
порог новой клинической нормой.

## 6. Синтетика и объединение веток

| Эксперимент | Обязательное условие |
|---|---|
| Поворот позвоночника | пересчитывать итоговый угол с учётом исходного знака: поворот на 6° не обязательно создаёт нарушение |
| Кроп / сдвиг | проверять все затронутые цели; ROI-аугментации только после определения ROI |
| Вставка посторонних предметов | доноры, параметры и подбор генератора только из train; проверка исключительно на реальных снимках |
| Геометрия + признаки изображения | сравнить каждую ветку отдельно и простое объединение на одинаковых внешних фолдах |
| Второй бэкбон | включать только при устойчивой дополнительной пользе; учитывать время полного инференса |

Синтетические варианты наследуют группу исходного исследования и не добавляют
независимых пациентов. Неконтролируемые повороты и кропы в обычном обучении запрещены.

Стекинг допустим после простых сравнений. Его обучающие входы — внутренние OOF-прогнозы;
внешний фолд не участвует в обучении ни одной стадии. Стекинг общего качества поверх
стекинга нарушений пока не планируем.

Среднее рангов по текущему входному пакету не используем: один снимок должен получать
тот же результат в одиночном запросе и в любом пакете. Если потребуется преобразование
оценок, его параметры фиксируются на обучающих данных.

## 7. Валидация и принятие решений

| Уровень | Правило |
|---|---|
| Внешняя проверка | 5 фолдов по исследованиям; распределение всех пяти целей проверено и сохранено до обучения |
| Внутренняя настройка | 3 групповых фолда внутри внешнего train, если состав целей позволяет; иначе заранее фиксированные параметры для проблемной цели |
| Что настраивается внутри | регуляризация, обучаемая предобработка, синтетика, слияние и пороги; локализаторы и доноры не видят внешний фолд |
| Пороги | выбирать по внутренним OOF; бутстрап может показать нестабильность выбора, но не заменяет независимую оценку |
| Основной отчёт | объединённые внешние OOF-прогнозы: бинарное качество по областям и каждая из пяти целей; F1, ROC-AUC, PR-AUC, чувствительность, специфичность, balanced accuracy |
| Диагностика | метрики и числа позитивов по фолдам, ошибки маршрутизации, геометрия отдельно, случаи отказа, подгруппы |
| ДИ | 2000 бутстрап-выборок исследований по внешним OOF, 95%; сохранять все снимки выбранной группы и её кратность |
| Финальное обучение | после выбора рецепта повторить внутреннюю настройку на всех размеченных данных, обучить финальные веса; качество сообщать по внешней оценке |

Распределение редких целей в стандартном разбиении — в
[аудите набора](context/HACKATHON.md#31-что-видно-в-самих-файлах). Балансируем несколько
целей на уровне исследований. Если валидное распределение невозможно, число фолдов
уменьшаем и документируем причину. Официальная агрегация отслеживается в
[Q03](context/QUESTIONS.md#q03--официальный-расчёт-метрик).

ROC-AUC при одном классе — `NA`; не заменяем нулём. Для остальных метрик фиксируем
поведение при нулевом знаменателе. В бутстрапе указываем число пригодных ресэмплов для
каждой метрики. Интервалы по фиксированным OOF отражают вариативность набора, но не всю
неопределённость повторного обучения и выбора архитектуры.

Повторы разбиения — только как отдельная проверка устойчивости, с явным перемешиванием
групп и сохранёнными назначениями. Обычный `GroupKFold(5)` не меняется от смены сида.
Не выбираем лучший сид по качеству.

**Один опыт — одно изменение.** До запуска записываем гипотезу и критерий принятия.
Смотрим парную разницу метрик на тех же исследованиях, ДИ и ошибки конкретных случаев;
при неопределённом выигрыше оставляем более простой вариант. Выбор лучшей из многих
архитектур по внешним OOF тоже создаёт смещение: такую оценку называем результатом
разработки, окончательная независимая проверка — закрытый тест организаторов.

Методическая опора: [вложенная кросс-валидация](https://scikit-learn.org/stable/auto_examples/model_selection/plot_nested_cross_validation_iris.html),
[настройка порога](https://scikit-learn.org/stable/modules/classification_threshold.html).

## 8. Выход и сервис

Состав колонок — в [HACKATHON §4](context/HACKATHON.md#4-формат-выхода),
правила заполнения и обработки ошибок — в [TEMPLATE §3](context/TEMPLATE.md#3-контракт-выхода--одна-функция-руками-таблицу-не-собираем).

| Компонент | Выбранное поведение |
|---|---|
| `quality_prob` | оценка общей бинарной головы; калибровку проверяем отдельно |
| Нарушения | отдельные пороги пяти применимых целей; `quality_class` определяется наличием выбранных типов |
| Оверлей | проверенные ориентиры; измерение и норматив отдельно от решения модели |
| API | план: `GET /health`, `POST /predict` для DICOM, `POST /batch` для архива с общей таблицей |

Если отдельная общая голова даёт высокую оценку без выбранного типа нарушения, это
фиксируется как расхождение целей и анализируется на проверке. `quality_class` по ней
независимо не переключаем и не добавляем несуществующий тип нарушения.

Время считаем для всей цепочки: чтение, бэкбон, геометрия, отчёт. Быстрые линейные головы
не определяют стоимость извлечения признаков. Проверяем [лимит задачи](context/HACKATHON.md#5-технические-требования),
обработку ошибочных файлов, независимость результата от пакета и повторяемость.

## 9. Порядок работ и точки остановки

| Этап | Результат | Условие перехода |
|---|---|---|
| 1. Данные и протокол | манифест, фолды и обработанные зависимости Q01–Q05 | выполнены условия соответствующих записей QUESTIONS; утечек групп нет |
| 2. Сквозной бейзлайн | один бэкбон, головы всех целей, API, таблица, контейнер | обработка пакета и внешние метрики воспроизводятся |
| 3. Ручная геометрия | пилот, инструкция разметки, ошибки измерений и правил | выбран хотя бы один полезный и наблюдаемый индекс |
| 4. Автоматизация | локализатор нужных ориентиров | измерения проверены независимо, известна доля отказов |
| 5. Сравнения | геометрия, синтетика, второй бэкбон — отдельными опытами | польза оправдывает сложность и стоимость |
| 6. Фиксация | финальные веса, чистый прогон контейнера, документация и демо | работает без репозитория и сети, формат соответствует контракту |

На упаковку, проверку и документацию резервируем последние два дня до
[сдачи](context/CONTEST_RULES.md#1-что-подтверждено); детали загрузки —
[Q10](context/QUESTIONS.md#q10--детали-загрузки-и-расписания). Если геометрия не проходит пилот, завершаем
сервис с бейзлайном всех классов.
Если новый компонент не даёт убедительного выигрыша, в сдачу он не попадает. Обязательный
функционал имеет приоритет над DICOM SR и дополнительными визуализациями.
